# Narration, voice-over, storyboard

## 1. Narration (`script/narration.txt`)

> **Read `narration-guidance.md` first**: this section only covers format, budget and the interface with the visual system; how to keep it from being boring (open on a situation, one throughline, cause before effect, tangible numbers, load-bearing metaphors, an ending that calls back) is in that set of principles, and once written, run its pre-flight checklist. The most common failure is retelling the reference material section by section in its table-of-contents order: it reads like a tool list. Those principles were written precisely for that.
Format:
```
# CHAPTER 1 Chapter name (≤6 characters, progress-bar chapter name)
One sentence|split by vertical bars into subtitle chunks|each chunk ≤16 characters        ← one sentence per line; the bars only split subtitles and do not affect reading
The next sentence in the same paragraph                                ← sentences within a paragraph are only 10 frames apart, no pause
                                              ← blank line = paragraph break: one paragraph = one shot, 30-frame pause at paragraph end (GAP+PARA_GAP ≈ 1 s)
A new paragraph (= the next shot)
## gap 20                                     ← optional: insert extra blank time before the next sentence (use when the last chunk of a paragraph-end sentence is too short)
```
Writing points (the sample `examples/rag/narration.txt` is a video that "explains a technology"; its structure is the solution to that topic, not a template):
- **Structure comes from the throughline, not from a genre template**: first, per `narration-guidance.md` §2, find the single throughline of the whole video: a process from start to finish, how a tension is resolved, how a puzzle is solved, how a comparison produces a winner... A chapter = one step along the throughline, and every chapter must be able to say in one sentence "why this step follows the previous one". The number of chapters depends on the content, constrained by length: <3 minutes is a single chapter (no chapter cards), 3-5 minutes is 3-4 chapters with each ≥60 s, 5-8 minutes is 4-6 chapters; chapter names ≤6 characters (progress-bar chapter names). If the chapters can be reordered freely with no loss, there is no throughline: go back and find it again.
- **Chapter names and HUD section names are navigation labels, not creative titles**: a viewer glancing at the progress bar should know what this part covers. Write them as noun phrases of "topic word + aspect / action", ≤6 characters (for English see §2.5), with parallel structure across the chapters of one video; the term currently being explained can go straight into the chapter name (repeating it on the progress bar helps viewers remember it).
  - Good example (sample video): `Why RAG / Building the knowledge base / Retrieval and generation / Evaluation and beyond`: copy these out for someone who has not seen the video and they can still say what each chapter covers.
  - Bad example (sixth video, called out by the user): `Feels okay / Set up and leave traces / Two rulers / Diagnosis and proof`: evaluative phrases, metaphors and quips, impossible to guess the content. Keep metaphors and punchlines for the narration and the visuals, **do not put them in the progress bar, chapter cards or HUD capsules**.
  - Three self-check questions: (1) Looking only at these words, can someone who has not seen the video say what each chapter covers? (2) Is each one a noun phrase (not an exclamation, an evaluation, or half a sentence)? (3) Read together, do they form an understandable throughline (parallel or progressive)? If any answer is no, rename.
  - The chapter name is **the only copy that can still change after the script is locked**: it is not read aloud and does not affect any frame number: edit the `# CHAPTER n Name` line in `narration.txt` and rerun `tts_build.py` (every per-sentence cache hits, a few seconds); HUD section names likewise, edit `hud[].text` in `config.ts`. So if the QC stage finds them unclear, there is still time to fix them.
- **Chapter boundaries need a setup, development, turn and resolution; do not just "finish and cut to the card"** (user feedback: one chapter ended, it cut straight to the next chapter title and started talking, and it felt disjointed). In a multi-chapter video, every chapter boundary must:
  - **Leave a hook at chapter end**: the last paragraph of the chapter states the problem, cost or gap the next chapter will address, so viewers themselves think "so what's next?".
  - **Open a chapter by carrying over before introducing the topic**: the first sentence refers back to what the previous chapter achieved, then poses this chapter's question: the sample video does exactly this: `The manual is built|the moment a user asks a question|is when the real exam begins` (chapter 2 built the knowledge base → chapter 3 retrieval), `The system is up|how do we know if it's any good` (chapter 3 → chapter 4 evaluation).
  - Two kinds of bad example: opening a chapter from scratch (`What is X`, jumping straight into a definition) → disjointed; only announcing (`Next let's look at X`) → an idle transition, the kind `narration-guidance.md` §10 says to delete. The difference and how to tell them apart are in §13: **no announcing, but do bridge**.
  - **The same goes for the visuals**: the first shot of a chapter should not clear the stage and redraw; use the hero / symbolic object from the previous chapter's last shot as the starting point (same component, same parameters, can be shrunk or moved), and the chapter's last shot shrinks it into a corner and hands over to the chapter card; in the storyboard, the chapter-opening row says "Carry-over: <element> brought over from SCxx". Writing the chapter card subtitle (`chapterTech`) as "previous chapter's output → this chapter's action" also counts as a carry-over.
  - A single-chapter video (<3 minutes) has no chapter boundaries, so this does not apply.
- **One thesis sentence per chapter**: put it at the start or end of the chapter; it is the candidate for that chapter's highlight moment (chapter thesis / hero entrance / closing payoff, see `composition-and-light.md` §3); the storyboard stage's list of highlight moments comes directly from these sentences.
- **The running example context is a hard constraint at the visual level** (SKILL.md hard principle 3): one concrete example for the whole video, all groups share the same set of example text, and it is written concretely the first time it appears in the script. Metaphors are not mandatory: per `narration-guidance.md` §5, use one only when it helps viewers reason, and once used, carry it through to the end; do not assign one per chapter.
- **Blank-line paragraphs = shots**: 2-4 sentences per paragraph, one paragraph finishes one visual unit; at paragraph end the picture holds 1-1.5 s before cutting, with no pause between sentences within a paragraph (one sentence per paragraph = a pause after every sentence = the whole video drags, user feedback). Paragraph-end sentences appear in `timeline.md` marked with ¶, and the storyboard divides shots by paragraph.
- Length: **use the row in the table that matches the length the user chose** (e.g. 3-5 minutes → 40-50 sentences, 1100-1400 characters). Speaking rate is about 5.5 characters/second (edge Yunxi at normal rate `RATE=+0%`, no speed-up by default; for English see §2.5); after adding paragraph-end / pre-chapter gaps, the final video density is about 4.0-4.5 characters/second (the final video is 5-8% longer than the pure voice track, which is the hold budget). Each sentence ≤35 characters; split long sentences with vertical bars into 2-5 chunks. **Short sentences are good copy** (rhythm variation, `narration-guidance.md` §7), no need to avoid them for the visuals: at the storyboard stage short sentences merge into adjacent shots as beats rather than becoming their own shots. Estimate the length once written; if it is over/under by 15%, add or remove sentences.
- Only use numbers that have a source in the research document's §number list; name the institution and year ("an experiment by some institution in 2024"); for volatile numbers add "at release / as of year X"; convert every number into a scale viewers can feel (`narration-guidance.md` §4), and if it cannot be converted, delete it.
- Chinese videos: the first time a foreign term appears, put the Chinese first and the foreign term after; abbreviations must be pronounceable, otherwise write the full name. For English videos see §2.5.
- Every sentence must be drawable: while writing, think at the same time "what does this sentence show": which kind of visual relationship it describes (left column of the pattern table in §4); rewrite or delete sentences that cannot be drawn.
- Use a process track (§3 persistent layer) only for steps with a strict order: not every chapter needs one, and not every topic has one.
- Chapter titles are the progress-bar chapter names; section names within a chapter are the HUD capsule words (later written into config.ts).

## 2. Voice-over (`scripts/tts_build.py`)
- **Before running it, pass confirmation point 2 (script locked) and confirmation point 3 (voice-over) in SKILL.md**: ask the user once whether they have a preferred TTS; if not, use the default. Do not lay out a pile of options for them to pick from.
- Engine (`TTS_ENGINE`, default `auto` picks by narration language):
  - `edge` **default for Chinese**. edge-tts, `VOICE=zh-CN-YunxiNeural RATE=+0%` (male voice; **normal rate by default, no speed-up**; if it feels slow, pass `RATE=+8%` yourself, which raises it from ≈5.5 to ≈6 characters/second); options: YunjianNeural (energetic) / YunyangNeural (newscaster) / XiaoxiaoNeural (female). It has word-level boundaries, so subtitle beats are the most accurate.
  - `kokoro` **default for English**. kokoro-82m local inference: `KOKORO_VOICE=am_liam KOKORO_LANG=a KOKORO_SPEED=1.0`: Liam, male voice, positioned the same as the Chinese Yunxi. Requires `pip install kokoro soundfile` + espeak-ng (macOS `brew install espeak-ng` / Linux `apt install espeak-ng`).
  - kokoro has no word boundaries → it synthesizes each subtitle chunk separately and concatenates them instead: chunk start frames are therefore still exact, but phrasing at chunk boundaries is a little stiff (`CHUNK_PAD` adjusts the silence between chunks).
  - `kokoro_onnx` / `piper`: local alternatives on Linux/ARM (Raspberry Pi) when `kokoro` will not install; both use the per-chunk synthesis path. `kokoro_onnx` sounds natural (`pip install kokoro-onnx` + `KOKORO_ONNX_MODEL` / `KOKORO_ONNX_VOICES`, `KOKORO_ONNX_VOICE` defaults to am_michael); `piper` is the fastest but rather mechanical (`pip install piper-tts` + `PIPER_MODEL`). Neither honors the `PRONOUNCE` pronunciation overrides. Installation details in README "Linux / Raspberry Pi".
  - The user has a preferred TTS (including a human voice actor / voice clone): do not run this script; put the finished file at `public/assets/<slug>/audio.wav` and fill `src/common/timeline.ts` and `subs.ts` yourself from the per-sentence/per-chunk timeline (format in the file header); the interface is the same.
- Per-sentence synthesis + WordBoundary → subtitle chunk start/end frames; GAP within a paragraph 10 frames, paragraph end +PARA_GAP 20 (at blank-line paragraph breaks, 30 in total), CHAPTER_GAP before a chapter 45, LEAD at the opening 40, TAIL at the end 90; volume normalized to a peak of 0.89.
- `timeline.md` has two extra columns: "last chunk" (frame count of the final subtitle chunk) and "para end" (¶ = the sentence before a blank line/chapter boundary, where the shot ends). The terminal lists **paragraph-end sentences whose last chunk is <45 frames**: final-beat element 22-frame entrance + 8-frame exit leaves less than 30 frames of hold. Add `## gap 15-30` after these sentences (no wording change, cache hits, rerun takes seconds), or in the storyboard move the final-beat element earlier onto the previous chunk. Sentences within a paragraph are not checked.
- Output: `public/assets/<slug>/audio.wav`, `src/common/timeline.ts` (TOTAL_FRAMES / CHAPTER_STARTS / SENTENCES), `src/common/subs.ts`, `script/timeline.json|md`.
- Per-sentence cache in `audio/cache/`; changing one sentence re-synthesizes only that sentence. **Do not change wording once storyboarding/building has started**: every frame number shifts, and build-group code hardcodes frame numbers.
- Validation: subtitle start vs audio start error ≈1 frame (you can read the wav with numpy and find onsets to double-check). Swapping in a human/cloned voice (e.g. VoxCPM2 + forced alignment) also goes through this "per-sentence synthesis + word-level timestamps" interface: synthesize it outside yourself, then fill the finished file and per-chunk frame numbers into `audio.wav` / `timeline.ts` / `subs.ts`.

## 2.5 English videos (`lang: 'en'` in `config.ts`)
All rules for the visual system, motion, composition and light apply unchanged; only the quantities below change with the language. **Before starting, set `lang` in `src/config.ts` to `'en'`** (`tts_build.py` prints ⚠ when they do not match), and leave `title.rest` empty `''`.
- **Length** (speaking rate: `edge-tts en-US` +0% measured 2.96 words/second; **kokoro `am_liam` speed 1.0 measured 2.30 words/second** (prose 2.25, abbreviation-dense sentences 1.4-1.8; measurements in `lessons.md`); after gaps, final video density ≈2.1 words/second → **write kokoro English videos at ≈125 words/minute**, 5 minutes ≈640 words / 48 sentences; the table below is on the edge-tts basis, multiply the word counts by 0.78 when using kokoro):

  | Length | English words | Sentences / shots |
  |---|---|---|
  | 2-3 minutes | 280-420 | 24-32 |
  | 3-5 minutes | 420-700 | 40-50 |
  | 5-8 minutes | 700-1150 | 60-80 |

- **Each sentence ≤20 words** (equivalent to ≤35 Chinese characters); split long sentences with `|` into 2-5 chunks. `tts_build.py` trims leading/trailing spaces from chunks and then **joins them back into the full sentence with spaces** for TTS, so `powerful|but they` and `powerful | but they` are equivalent and will not be read as powerfulbut.
- **Each subtitle chunk ≤48 characters** (≈7-8 words). Measured: at 49 characters the 44px text already has to shrink, and >70 characters wraps to two lines and pushes into the content area. `tts_build.py` checks every chunk at generation time and lists the ones over budget.
- **Terms**: the first time, write the full name + abbreviation in parentheses (`retrieval-augmented generation (RAG)`), and use the abbreviation from then on; there is no "Chinese first, English after" rule. Abbreviations must be pronounceable (RAG / HNSW / BM25 are read letter by letter).
- **Chapter names** (progress bar): naming rules as in §1 (say what the chapter covers, no metaphors or evaluative phrases). Slot width = 1280 ÷ number of chapters; at 24px each slot caps at about 25 characters, **≤14 characters is safest** (beyond that it auto-shrinks to 17px). Chapter card titles at 80px fit about 22 characters at most, beyond that they auto-shrink.
- **Chapter card subtitle `chapterTech`**: Chinese videos use a "big Chinese text + small English text" structure; in English videos do not translate the title twice: write a shorter kicker, or just leave it empty `''` (empty means it is not rendered).
- **Voice-over**: default kokoro `am_liam`; if you want word-level boundaries (most accurate beats) use `TTS_ENGINE=edge VOICE=en-US-AndrewNeural` (cloud). kokoro spells out uncommon abbreviations letter by letter and reads version numbers like "v5.0" as "v five zero": dump the phonemes before synthesis to check, and override in the `PRONOUNCE` table in `tts_build.py` with `[word](/phonemes/)` (it only changes the text sent to TTS, subtitles are unchanged; **only works with the kokoro engine**, piper / kokoro_onnx do not understand this syntax).
- **English punctuation**: Noto Sans SC's curly quotes and ellipsis are 1em full-width glyphs; on screen use straight quotes and three periods.
- **Typesetting**: no horizontal compression, no baseline pre-offset when centering, width fallback: all applied automatically by `lang`, see `style-guide.md` §3.1.
- The finished English video "RAG & Knowledge Bases" is the video at the top of the README (5′02″, kokoro `am_liam` at natural rate, derived from the Chinese version by re-timing frame numbers shot by shot); process files (storyboard, source, QC) exist only for the Chinese sample, **use `examples/rag/frames/` as the visual yardstick** (the graphic language is language-independent).

## 3. Storyboard (`script/storyboard_src.md` → `storyboard.md`)
Tokens: `{S12.from}` `{S12.to}` `{S12.c3}` (start frame of the 3rd subtitle chunk) `{C2}` (start frame of chapter 2) `{TOTAL}`, may carry ±integer: `{S12.from-8}`. `python3 scripts/render_storyboard.py` fills in the frame numbers.
Structure (follow `examples/rag/storyboard_src.md`):
1. Header: total frames, chapter frames, transition rules (shot range = [first sentence from−8, next sentence from−9], at chapter end / video end = last sentence to+2; exit in the last 8 frames; element entrances aligned to subtitle chunk start frame −6…+3; final-beat settle → exit ≥30 frames; no camera move in the final beat). **Shots are split by visual unit, not by sentence**: one paragraph (between two blank lines in the narration) = one shot, short sentences (<3 s or a single chunk) merge into an adjacent shot as beats, a single shot is ≥120 frames, and if you can hand off, do not clear the stage.
2. Persistent layer table (overlay, owned by the main session): opening, chapter cards, HUD entry ranges, process track steps and switch frames, ending; chapters with a track are marked "main content area y175-620".
3. One table per group (two groups per chapter, numbered G1-Gn consecutively), one row per shot: `| Shot | Frames | Beats (subtitle chunk start frames) | Visual | Motion | Hero·size | Light |`. Visual describes elements, positions (reference coordinates), color semantics; Motion describes the entrance method + which beat it aligns to + the exit method + **camera move** (≥3 per chapter: push-in / hand-off move / whole-group pan / parallax, see motion-vocabulary.md §camera moves) + **two closing sentences "Sustain: ..." and "Hold: ..."** (Sustain: the action through which this subtitle chunk's verb continues on screen until the next beat: data flow / a pulsing light dot running along an arrow / line-by-line typing / cells lighting one by one / growth / a gate opening and closing / a queue compressing; for a shot with no other camera move write "1.0→1.05 slow push", **never write floating / drifting / breathing**; Hold: the number of frames from the final-beat element's settle frame → exit start, ≥30, target 30-45, and if short, state how it is made up: move earlier / `## gap` / merge shots; rules in `composition-and-light.md` §7); **Hero·size** gives this shot's single hero and its height (graphic ≥170px or big text ≥96px, entering on the 1st-2nd beat); **Light** gives what light the hero carries and which item is currently in focus (rules in `composition-and-light.md`, bad examples in `examples/contrast/`); **"glitch" is written only on that shot's one key word**, everything else says "fade in/slide in/scale".
4. Global constraints: example context (original text of the question/answer/source copy), fact list (numbers/English allowed to appear on screen), glitch whitelist (key word for each shot), list of reused graphic elements, **chapter boundary list** (one row per chapter boundary: the hook in the previous chapter's last sentence / the carry-over sentence at chapter opening / the element carried into the chapter's first shot and its source shot, see §1 "chapter boundaries need a setup, development, turn and resolution"), **highlight moment list** (≤1 shot per chapter: chapter thesis / hero entrance / closing payoff, each tagged entrance type / thesis type / big-number type / symbolic-object type, choreographed per `composition-and-light.md` §3, ≥90 frames), **sweep whitelist** (entrance type only, ≤2 shots in the whole video: first entrance of the core concept + an optional callback at the end; no other shot may contain `LightSweep` / `StageLine` / `GhostText`), **camera move list** (≥3 per chapter, stating which shot, which beat and which kind), **§9 sustained action and settle hold** (copy verbatim the two rules and quantitative criteria from `composition-and-light.md` §7: no completely still element for >3 s after entrance, no floating added just for motion, after the final-beat settle hold 30-45 frames before exit, no camera move in the final beat; build groups self-test with `scripts/motion_check.py <Gn>`).
