# Lessons and root causes (each entry corresponds to a real round of rework; after each new film, append new lessons here)

## Build artifacts (best practices)
- Put only this film's assets in `public/` (the template is 18MB, the bundle ≈38MB); render stills only with `scripts/still.sh`, one fixed tag per group, and after changing code `rm -rf build_dev_<tag>` before rebuilding; do not run `npx remotion still src/index.ts …` directly (it leaves a temporary bundle in $TMPDIR; the script already cleans it up automatically).
- Background scripts always use absolute paths (the shell cwd drifts).

## Writing the storyboard
- "Last 2 frames do not exit + hard cut to the next shot" gets read by both sides as "I don't move, you only enter at the beat frame" → 6-8 frames of empty screen at group boundaries/between shots (5 places in one film). Write it as "A fades out to zero over its last N frames + B starts entering from its first frame".
- Exits before a hard cut must reach zero: an exitFade of 6.7%/frame still has 40-57% left on its last frame, and in motion it "pops". Use 1−(n/N)^1.5.
- A slide-in from below with Δ≈300 crosses y637-690 in films with a subtitle band (6 places in one film). Use Δ≤120, or a sideways slide-in + fade-in over the first 6 frames.
- For staggered entrances of multiple elements, don't use GlitchIn (5 pills each flicker randomly and drop frames); use staggered slide+fade.
- Write the word "glitch" only in the one key-word cell per shot, otherwise the build agent adds flicker to all text (102 places in one film, vetoed by the user).
- Coordinates given in the storyboard are reference values, and build groups may fine-tune them for the safe area; but example text, color semantics and graphic elements must be followed exactly.

## Overlay layer / structure
- The overlay's darkening/fade-out must be above the content (at the end of the SHOTS array or aboveBar), otherwise the last shot disappears with a hard cut when its own Sequence ends.
- Exit animations need enough frames: an 8-frame exitAccel(1.2) only travels 59px/63% brightness before being hard cut; 12 frames, 440px + opacity to zero is clean.
- Adjacent HUD entries in the same chapter must have no gap (extend the previous one to the next one's from−1); fade out 8 frames before entering a chapter card; offset HUD word changes from big content glitches by 4 frames, otherwise everything goes black on the same frame.
- Fade the flow rail out over its last 8 frames; do not make it vanish in one frame.
- Preview compositions (each group = overlay layer + that group's shots) let build groups see the relationship between the HUD/flow rail and the content.

## Code
- kf first-value trap: t < first keyframe returns the first value; entrance tables must start with [shot start frame, off-screen value], otherwise the element sits in frame early.
- Draw-on elements like Check/Cross must return null at p=0 (the linecap shows a dot).
- Color-mixing functions must parse both rgb() and hex (nested parsing produced NaN and made all 25 cards invisible).
- blur σ<0.8 has no effect in Chromium; feConvolveMatrix goes down the software path at 0.13 fps and is banned; add colorInterpolationFilters="sRGB" to SVG filters.
- The CJK line box ascent puts the ink 3-7px below top; pre-subtract dy −2…−5 for centered text.
- Minimum font size is 22px (QC measures ink height); superscript badges may be an exception at 20px.

## Voiceover / timeline
- Do not change wording after it is final: build groups hard-code frame numbers in code. To change, change the words first and then realign everything.
- TTS word-boundary start vs audio onset error ≈1 frame; when detecting onset, don't let the window reach into the tail of the previous sentence (it will misread −15 frames).
- When rejoining English `|` chunks into a full sentence, add spaces between chunks (once `powerful|but` was joined into powerfulbut and sent to edge-tts); the chunk start cursor must also skip that space.

## Multi-agent
- Give one agent only one heavy job (build 5-7 shots / QC one chapter / fix 1-2 groups); a second job should only be a light one. An agent that has already read many images and is then given a heavy job dies with "input too long" ~30% of the time.
- Agents killed by API errors: one SendMessage can wake them; if not, TaskStop and reassign.
- Build groups will deviate reasonably on their own (swap example text, add full Chinese names, change topology, shorten frame counts); if there's a source, let it through, rule on it in one sentence, and record the ruling in BUILD_NOTES.
- QC reads brightness as int32 (int16 overflows to all zeros).

# Film 2 "eCPM and Ad Auctions" (2026-09-07, 48 shots / 4′16″): new lessons

## Beats and reading time (the two most systematic classes of defects in this film)
- **Do not hang the gray source/basis fine print on a shot's last subtitle block.** The storyboard put sources on the last beat by default, so 40-70 characters of gray fine print stayed at ≥50% α for only 0.97-1.7 s and could not be read in time: one of them was a corrective line "to prevent viewers from mistaking the formula for the current definition", which was effectively never delivered (QC rated it high). **Criterion: source fine print must stay at ≥50% α for ≥2.5 s (≥75 frames) within its shot; how to write it: hang f0 on the shot's 1st-2nd subtitle block** (it is background basis and does not need to follow the narration). All 8 instances in this film were reworked.
- **The first 8 frames of the shot interval `[sentence from−8, sentence to+2]` are the entrance budget; don't waste them.** If the first batch of elements waits until the subtitle block start frame to move, the start of the shot is an empty screen; at group boundaries (where the previous shot's last 8 frames already went to zero) this stacks into 11-16 consecutive pure black frames. 9 shots in this film were hit. **The first batch's f0 = the shot's first frame.**
- **Last-beat animations overflow the shot's end.** From the last subtitle block to the shot's end there may be only 20 frames, so a 22-frame slideUp or a 14-frame Cross draw-on does not fit: in the final film this shows as "some element never appears for the whole shot, then suddenly appears fully at the next shot's first frame". When dispatching, compute the remaining last-beat frames for every shot.

## `fadeIn` and the first frame
- **`fadeIn(n, len)` returns 0 at n=0, so using it for a shot's first-frame entrance always leaves one empty frame.** Use `softOp` (first frame ≈25%).
- A subtler layer: **`softOp(0, 8)` = 25%, and a white stroke's brightness is only 65, still under the "brightness >70" empty-screen criterion**: to make the first frame measurable, write `softOp(n+1, 6)` (first frame ≈57%). Likewise, the purple stroke `#A175F1` (brightness 144) is only 62 at 43% α and can't be measured either; if you want the entrance's first frame to be measured, use a white stroke or raise the starting α.
- **Don't wrap another `fadeIn` around a component that already has its own opacity ramp** (double fade-in): it dips for a frame or two at transitions.
- **Don't render the same element twice** (one always-on `SoftIn` copy + one `GlitchIn` copy): the always-on copy completely covers the flicker, the measured brightness stays constant, and the flicker is as good as not done. Either use a single instance with `glitchOpacity(n)` multiplied onto that same element, or hide the always-on copy during the flicker window.

## Factual compliance of numbers
- **The intermediate values of a counting animation are also "numbers on screen".** Linearly counting years 1995→1998 makes 1995/1996/1997 clearly readable for 4-6 frames; milliseconds 0→120 flash `37 ms`/`88 ms`; eCPM 0→30 flashes `8`. None of these are in the fact list. **General rule: if intermediate values are numbers that "look like facts but have no source", either make them unreadable or don't count.**
- Making years unreadable needs to be aggressive: blur `6.3→1.3px` leaves intermediate years clearly readable; `12→2px` with the final stretch ≤7px still leaves the second-to-last year legible for about 2 frames; **finally `12→9px` (≥9px throughout the roll) + back to 0 on the landing frame** is clean. Now packaged in the template as `YearRoll`.
- **Self-built illustrative examples must be consistent with other labels on screen.** Two failures in this film: (1) a live counter "+2405 this second", immediately followed below by gray fine print "billions of times a day": the two differ by 30x; (2) the value-bar formula computed the 8th bar ≈34, while the screen itself labeled it "≈ 1/5" (should be 24). **Before dispatching, cross-check every self-built example in the storyboard.**
- One more check method: **statically extract all literals that will appear on screen from the source code and reconcile them against the fact list.** QC samples frames from pixels and can't see frames that weren't sampled; source reconciliation scans all 8 groups at once, and that's how this film caught the counter (all four QCs missed it).

## Fonts
- **`Orbitron[wght].ttf` does not contain `¥`(U+00A5), `≠`(U+2260), `≈`(U+2248)** (verifiable with fontTools). Keep the fallback chain `'Orbitron','Audiowide'`: Audiowide is also geometric, and its ¥ matches Orbitron digits (measured at 3x zoom; switching to fallback Noto was a worse fit). Use `FONT_HEAVY` directly for `≠`/`≈`.
- **Orbitron's slashed zero (Ø) is fine inside multi-digit numbers, but isolated as a single `0` it reads as an icon** ("0 clicks" read as "Ø clicks" in the final film, and the illustrative value lost its meaning). **Switch an isolated single `0` to `FONT_HEAVY`; `1`-`9` glyphs are unambiguous and can stay.**
- **`Counter`'s default font family is `FONT_HEAVY`, not Orbitron**, which conflicts with the style guide's "numbers use Orbitron": four groups in this film reported it at the same time and each worked around it by building their own. The default has been changed to `FONT_ORB` and a `family` entry point added.

## Graphic elements and layer order
- **Verify the geometry of rotating elements before drawing them.** The old `GavelIcon` drew the hammer head 76 units above-left of the pivot and the sound block 101 units below the pivot: **the distance from the hammer head to the pivot is much greater than the distance from the pivot to the contact target, so a small ±26° rotation, positive or negative, only sweeps the head around up high and never touches the block** (QC measured the head's centroid y 507→499, moving upward). This is not a parameter problem. Correct form: the contact object lies horizontally above the target, the handle is vertical, and the pivot is at the top of the handle.
- **Don't let gavel-strike actions stop in the "contact pose".** After the rewrite, `angle=0` is "thin vertical handle + head pressed on the block", and staying in that pose for long reads as a rubber stamp/toilet plunger (two groups found this independently). After striking, lift back to −18…−24°.
- **Don't cram draw-on crosses/checks into the same `<Svg>` as arrows.** If that `<Svg>` is ordered before the card component, the cross gets completely covered by the card's black background: it shows up as "this cross never appears in the whole film", which is easy to misdiagnose as a timing problem. **Any mark that must sit on top of a card needs its `<Svg>` ordered after the card.**
- When an element draws its `title` **above, outside the card**, note it in a comment, otherwise in chapters with a flow rail it will hit the rail; drawing `xLabel` at `cy = h−8` makes 18px CJK ink crush the card's bottom border (all three cards in this film were hit).

## Overlay layer
- **The progress bar's current-chapter highlight must switch at the chapter card's start frame, not the chapter's first sentence start frame.** Otherwise during the 45 frames when the chapter card announces "02 One Auction" in the center of the screen, the bottom progress bar still highlights the previous chapter, and the two pieces of information contradict each other.
- **Don't make the flow rail's current-step switch a 1-frame hard cut** (gray bg ↔ purple bg flipping on the same frame), which is inconsistent with HUD word changes "always 8-frame fade-in". Add a 7-frame cross transition.
- The flow rail's upward-float Δ on entrance must be ≤22: Δ40 makes the pill sink to y184, crossing the spatial contract "in shots with a rail, content does not go into y<175".
- The fade-in frame count of the closing `EndingTop` determines how long the "final pure black" lasts: 20 frames leaves only the last 11 frames pure black; changing to 10 frames gives the last 19-21 frames.
- **The start frame of the closing fade-to-black eats the last shot's closing action.** With `endingFade=30`, the fade-to-black starts at "last sentence end −30", and this film's closing gavel strike originally landed after that, so the film's final action was completely invisible. When dispatching, schedule the last shot's actions before the fade-to-black, or reduce `endingFade`.

## Multi-agent
- **tmux/fork has a limit, and it is shared across the whole machine.** This machine had 13 other Claude sessions open at the same time, and when dispatching the 8th build group we got `respawn pane failed: fork failed: Device not configured`; two retries failed to start: the main session had to take on a whole group (6 shots) itself. **Before dispatching, check machine-wide usage with `ListAgents`; reserve 1-2 panes for later QC/fix rounds; TaskStop finished agents promptly to free them.**
- **"Append as you check" is a hard requirement for QC agents, not a suggestion.** In this film one QC agent saved everything for a final write, ran for an hour with zero output and did not reply to messages, so it had to be TaskStopped and reassigned (when reassigning, give it the conclusions the main session already found and have it do QC+fixes together, which was actually faster).
- **Don't copy agents' self-assessments verbatim.** Spot checks in this film found: one group self-assessed "intermediate years blurred and unreadable", but the actual output was clearly readable (it admitted in its own retrospective that "the self-assessment of §6 deviation (1) was too optimistic"); another group reported "changed to call the shared exitOp" while the disk timestamp looked earlier (on investigation this was my misreading, and the report was correct). **Conclusion: spot-check reports, but also don't rush to conclude the agent is wrong: look at all the evidence first.**
- **Build groups will find errors in the storyboard itself; encourage this and rule quickly.** The three most valuable improvements in this film all came from build groups: the value-bar formula contradicting its on-screen label, the factual-compliance hole in the year dial, and, following from that, proactively deviating by not counting milliseconds. When ruling, generalize it into a film-wide rule and write it back into the storyboard, which is worth far more than approving a single point change.
- The main session should keep **checks complementary to QC** for itself: static frame-coverage analysis (frame intervals/gaps/overlaps), reconciling source literals against the fact list, and source-level counting of the flicker whitelist. None of the three need rendering, they run in seconds, and everything they catch is something QC can't find from pixels.

## Style transfer (2026-09-08 retrospective: "Ad Auctions" made with the skill vs the sample film "RAG")
- **The skill wrote prohibitions but not the aesthetic drivers**: safe areas, whitelists, zeroing and beats all carried over (the new film was even better on these discipline items), but "how big to draw, what glows, how to choreograph highlight moments" lived only in the head of the person who made the sample → the new film's median subject height 172px vs 219px, the largest object <110px for 29% of the duration, protagonists were all unlit white wireframes, and highlight moments were handled with "pill + icon + one line of text". Fix: hard rules in `composition-and-light.md` + add "Protagonist·size" and "Light" columns to the storyboard + a highlight moment checklist.
- **Nobody read the sample film's source code**: the 8 build groups' BUILD_NOTES mentioned shots_src zero times, and the light-effect elements (LightBar/HaloRing/GhostText) stayed in the sample's group files rather than the template → one group in the new film reinvented LightBar. Fix: promote light-effect elements into `template/src/fx.tsx`; the last column of the pattern table gives the source path, and the build prompt changed from "may reference" to "must read".
- **QC only checked for defects, not "empty / small / dark"**: four rounds of QC all passed, and the picture was still small and dark. Fix: `scripts/frame_metrics.py` measures largest-object height / protagonist-area soft glow / fragments, written into the QC criteria and final check.
- **Camera movement was suppressed by this very doc**: the old build-rules said "mainly static shots", so both the sample and the new film had only 2.2-2.5 moves/minute and zero push-ins, while the original film that was the style source has 6.6 moves/minute, averaging 16 frames, including push-in/pull-out parallax. Fix: `CameraRig` component + camera movement budget (≥3 per chapter) + camera movement list in the storyboard.
- The two films have almost the same amount of motion, rhythm and total soft-glow area (per-frame change 0.47 vs 0.56, events 72 vs 76 /minute): **the gap is not in "how much it moves"**; don't try to fix it by adding motion.

# Film 3 "Cinematic Camera Movement" (2026-09-08, 50 shots / 4′00″, after one QC round high 0/medium 0/low 14): new lessons

## When the topic itself is geometric: build a real one first, don't fake it with CSS
- The central thesis of this film is "perspective is determined only by camera position, not by focal length". **If the picture fakes it with `scale`, push-in and zoom look exactly the same, and the whole chapter teaches the wrong thing.** So a real pinhole projection was implemented in `ui.tsx` (`project3` / `FrameScene` / `camOrbit` / `camDollyZoom`): push = only change `cam.z`, zoom = only change `cam.f`, pan = only change `cam.yaw`... QC verified pixel by pixel: in SC37 the person in both frames is 275/275px, equal, while the background door height is 197 vs 158px (20% different); in SC38 the person stays constant at 164px throughout while the back wall goes 506→360px. **The thesis is therefore "proven by the picture", not "claimed by the narration".**
- General rule: **for any topic where "two approaches look alike but are actually different" (push vs zoom, tilt vs crane, a real long take vs a fake long take), the underlying mechanisms must actually be different**, otherwise the two pictures the viewer sees will be identical.
- The flip-side cost: real projection brings a whole new class of defects (frames going empty, objects leaving the frame, person size leaving the safe band); see the next entry.

## Before dispatching 8 agents, run the shared system once with a probe
- I first wrote a `_probe.tsx` that rendered 8 camera states, one frame per cell, producing 8 images to glance at. **On the spot it caught two problems that would have made all 8 groups do it wrong**: (1) at `pitch=−22°` the frame is almost completely empty (the person is 180px but the frame is 332px; the person is entirely inside the frame, and any pitch change sweeps them out, leaving only floor); (2) with the default `personZ=520` the person is only 165cm from the back wall, and the background difference between push and zoom is only 12%, **not visible to the naked eye**: the person had to be moved closer to `personZ=320` to get a 26% difference.
- If these two had not been found in advance, the three shots SC17 and SC37/SC38 (including two highlight moments) would all have been scrapped. **The probe cost 10 minutes; the rework would have cost 3 groups.**
- The probe's output should become a measured **"camera parameter quick reference"** table in the storyboard (a `cam.z` → on-screen person height table + safe band 150-300px), so dispatches hand over numbers directly instead of letting each group step on it.

## Cross-group consistency: put constants in the shared layer, don't make agents align with each other
- In v1 I initially had "G6 builds the matrix, G7 reuses it" and "G5 reuses G3's spacing labels": as a result G7 had to import across groups, G6 and G3 each kept a parameter-by-parameter copy of `PinCross`, and whenever G3 changed, G5 changed too.
- A better approach (adopted for the second half of this film): the main session **first puts cross-group shared things into `ui.tsx`**: `LAYOUT` (layout coordinates), `frameInner`, `frameMarks` (bounding boxes of door/person/letter, computed with the same projection), `ACTION_WORDS`, `softOp` / `exitZero` / `mix` / `Vignette` / `MarkBox`. The eight groups import them directly, naturally consistent, with zero coordination cost.
- The concrete form of the lesson: **`softOp` was written by four groups separately, and the four formulas differed** (G1/G2's return 0 at n=0 and compensate by passing `n+1` at the call site; G3/G4's put the +1 inside the function). The protocol repeatedly said "use softOp, not fadeIn" but never provided it in the shared layer, which forced every group to invent its own. **Tools mentioned by the protocol must actually exist in the shared layer.**

## The "clear stage → light sweep" opening of a highlight moment itself gets flagged as an empty screen
- Both "high" items in v1 had this shape: SC12 (thesis type) had only one stage light line + one light-sweep strip in its first 79 frames, largest object ≤46px; SC40 had only five inactive dark frames + one pill in its first 66 frames.
- `composition-and-light.md` §6 says "the light sweep / stage light phase (content-area soft glow ≥10000px²) does not count as an empty screen": but **one round of light sweep doesn't reach 10000px² of soft glow** (measured 5004px²). So the "clear stage opening done per choreography" actually triggered the empty-screen criterion.
- Two fixes, best to do both: (1) **increase the light sweep to three rounds** and double the `StageLine` glow radius, so it truly falls into the exemption zone; (2) **give a temporary protagonist on the 1st beat** (this film carried over the previous shot's big text shrunk to 120px, or made that beat's keyword directly into 96px big text, then shrank it on the next beat to make room).
- General rule: **for entrance-type/thesis-type highlight moments, separately compute "how big the largest object is in these frames" for the first 60-80 frames**; don't assume "clear stage + light effects" passes automatically.

## Closing fade-to-black vs the last subtitle block: compute it, and compute it twice
- lessons already has "the closing fade-to-black eats the last shot's closing action"; this film hit its **upgraded version**: not an action being eaten, but **the film's concluding big text was fully readable for only 6 frames (0.20 s)**.
- The cause was three things stacked: the last subtitle block starts at f7067 → `GlitchIn` 12 frames (**7 of which have the text off**) → the fade-to-black starts eating brightness at f7085. Of the 18-frame window, only 6 frames were readable.
- **Criterion**: `(S_last.to − endingFade) − last subtitle block start frame ≥ 30 frames`, otherwise the conclusion can't be read in time. Half of `GlitchIn`'s 12 frames are "off", so **the actual readable time is only half the window**: when using glitch for closing big text, budget double.
- This film's fix: move the **whole sentence** conclusion forward to the second-to-last beat (f7043) with a single entrance, and let the last beat carry perceptible change through "light in motion" (denser halo ripples + soft-glow pulse + stroke fading in). **Note that the moved landing point must not sit on a white-flash frame**: QC found that the f7040 I originally proposed was exactly the first frame of a camera-move white flash, and a glitch landing on it would read as "the flash broke", so it was changed to f7043.
- This table should be computed for the last shot at dispatch time: last subtitle block start frame / fade-to-black start frame / whether there is a white flash in between / effective readable frames of the glitch.

## Transform scaling drags font sizes down
- In SC34/SC39 the ten action pills used `scale(0.72)` for the carry-over displacement, turning 26px text into **18.7px**, below the "minimum font size 22px". QC couldn't detect it from pixels (it measures ink height; 18.7px CJK ink is about 14px and is easily let through as a "small label"); build group G7 calculated and reported it itself.
- **General rule: wherever a whole group gets `scale`/`transform`, multiply every font size inside by the scale factor and check against the 22px floor.** The fix is to change the source font size (26→31, 31×0.72 = 22.3), not the scale.

## Diptych layout: the left and right halves must truly be the same camera
- This film's main layout is "top-down floor plan on the left + viewfinder frame on the right". In v1 the floor plan drew the door on the **left wall**, while in the frame the door was on the **back wall**: the two halves contradicted each other, and the floor plan's view frustum didn't contain the door at all. QC saw it at a glance.
- Cause: `roomAnchors()` was illustrative coordinates I hand-wrote for "a nice-looking floor plan", while `SCENE` was written from world geometry, and the two were never aligned. **Fix: derive the floor plan's door position from `SCENE`** (world x=−245 normalized within x∈[−440,440] is 0.2216), and draw the door on the top wall.
- But also recognize the cost: **changing the floor plan into a strict projection of `SCENE` would move the frustum angles every group had already tuned.** This film only did the low-risk half (door position corrected + envelope shrunk); the rest (camera orientation, frustum angle, room proportions) was recorded in the delivery notes as "an illustration, not a strict projection". **Changes like this must either be done before dispatching, or you admit it is an illustration.**
- The same graphic element having inconsistent colors in different groups also belongs here: `FovCone`'s default color is purple, G5 explicitly passed gray, G6 used the default → the frustum colors differ between the first and second halves of chapter 3, which was also the main cause of SC35's "purple fragments ≥8". **Set defaults per the spec (supporting roles don't glow → default neutral gray); don't let "whether a parameter was passed" decide the style.**

## Room/scene geometry: think through "where the camera will turn" first
- `SCENE` initially had only a back wall, and only to x=±440, with no side walls. As a result, **large pans (|yaw|≳8°), orbits and trucking moves exposed swaths of pure black on the frame's leading side**: G3 was forced to reduce a whip-pan landing from +42° to +22°, G4 was forced to cut the yaw difference between SC19's two frames from 60° to 26°, and G6's SC32 needed a 55° orbit (at θ=55° the back wall's right edge only reached 61% of the frame, 39% empty).
- Adding two side walls (drawn segment by segment + visibility tested segment by segment, degrading gracefully after pushing past a side wall) saved three groups with one change, **and the side walls' perspective convergence lines actually became the best evidence for "trucking has parallax" and "the background alone gets pulled away"**: G5 and G6 both proactively reported the effect got better.
- General rule: **design scene geometry for "the most extreme camera move"**, not for what looks nice from the default camera position. Before dispatching, list the angles/displacements of all camera moves and ask "at this angle, what is on each of the frame's four edges".

## Multi-agent (new in this film)
- **Hit the pane limit again, and earlier than last time**: this machine had 14 other sessions open at the same time, and I got `respawn pane failed: fork failed: Device not configured` at the **5th** agent (the previous film was the 8th). **Fix: dispatch in waves of 4, and only dispatch the next wave after one wave completes and is freed with `TaskStop`**; check machine-wide usage with `ListAgents` before dispatching.
- **Two QC agents were killed by API errors** ("The response stopped arriving", ENOTFOUND). One `SendMessage` woke both, and they finished. **But waking only preserves the part already written to disk**: so "append as you check" is a hard requirement, not a suggestion: in this film one QC agent was still at 0 bytes after 46 minutes, and only started writing after I nudged it once; if it had died first, everything would have been lost.
- **Quantitative QC verification is worth much more than "looked at the image, OK".** The most valuable QC output in this film was two sets of per-pixel readings (SC37's 275/275px and 197/158px, SC38's constant 164px and 0.711x): they turned "the thesis holds" from a subjective judgment into reviewable evidence, written directly into the delivery notes. When dispatching QC, **name which readings you want**.
- **QC will correct the main session's fixes.** For SC50 my proposed fix was in the right direction, but QC measured that the landing point f7040 sat on a white-flash frame, and that `CamIcon`'s entrance path crossed the conclusion's text line: its three-line corrected version was more complete than my original. **Before dispatching a fix order, have QC check your own fix first.**
- **The static check the main session wrote itself (`scripts/selfcheck.py`) is worth keeping for every film**: frame coverage (50 shots continuous with no gaps, reconciled against the storyboard's frame intervals), source-level counting of the flicker whitelist, and reconciling on-screen literals against the fact list. It runs in seconds and catches things QC can't find from pixels (e.g. words like `Danny`/`Jack`/`MOVE`/`Dolly` that were not in the fact list). **Write the noise filters well** (filter out import paths, CSS values, camelCase identifiers), otherwise it reports a pile of false positives that nobody reads.


## One-minute "Agentic RL" (2026-09-09): new lessons
- The newer edge-tts Communicate may default to SentenceBoundary, while the old tts_build.py only accepted WordBoundary, silently leaving an empty list and degrading to subtitles estimated by character count. Pass `boundary="WordBoundary"` explicitly; on a cache hit, check that word boundaries are non-empty, and if there are none, stop rather than falsely reporting precise sync.
- After shortening CHAPTER_GAP for a short film, the HUD's existing rule "gap <30 frames means same chapter" made the previous chapter's pill cover the next chapter's chapter card. Compare by the sentence's chapter instead of guessing from the gap. The progress bar highlight should correspond to the start of the chapter card.
- An opening of only 40 frames needs its motion budget re-choreographed; you can't cram in the long opening's default glitch, subtitle subheading and push-in. This film finally chose a uniform 6-frame fade-in for three lines, followed by a 33-frame eased gentle push-in; there's no need to force flicker in the opening.
- A test-render directory generated by `mktemp` with a dotted suffix may be rejected by Remotion 4.0.507 as an output extension. A dotless directory like `explainer_test_TAG_XXXXXX` outputs image sequences normally.

# Film 4 "The AI Systems Performance Engineer" (2026-09-10, English, 48 shots / 5′07″, 9 groups, one QC round, high 0): new lessons

## Speech rate and pronunciation in English films
- **kokoro `am_liam` at speed 1.0 measures ≈2.3 words/second (prose 2.25, acronym-dense sentences 1.4-1.8), not edge-tts's 2.96**. A 5-minute English film is ≈640 words / 48 sentences; writing 700+ words per the table in SKILL.md would overrun to 6′17″. On the first run, synthesize the whole script and read the `speech=` value before adjusting length (that's how this film cut 733 words to 642).
- kokoro spells out CUDA / NIXL / MIG / DeepGEMM letter by letter and reads v5.0 as "v five zero". The `[word](/phonemes/)` override syntax works and is now the `PRONOUNCE` table in `tts_build.py` (it only changes the text sent to TTS; subtitles stay the same). When dispatching the researcher, have it list all acronyms too, and dump phonemes (the `ps` returned by `KPipeline`) for checking before synthesis.
- **Noto Sans SC's curly quotes “ ” and … are 1em full-width glyphs**, leaving a big gap in English; always use straight quotes on screen (found by G9).
- `Pill`'s `textDy` default of −2 is a Chinese baseline compensation; English films should follow `TEXT_DY`; the template has been changed.

## Narration: retelling the reference's table of contents section by section = a tool list
- The first version's 48 sentences followed the reference book's section order, and the user's first reaction was "too rigid and boring"; a version rewritten independently from writing principles won a blind rating 8.2 to 4.3. The root cause was no through-line: chapters could be reordered at will with no loss. Fix: the principles became a separate doc, `narration-guidance.md`, required reading upon entering stage 2; `narration-storyboard.md` no longer prescribes a fixed chapter structure, keeping only format, budget and the visual interface, and the left column of the shot pattern table was changed to topic-independent "visual relationship types".

## "Enter and then stop" is a defect: verb-driven continuous action
- After watching a 30-second sample, the user's first reaction was not about style but "can you describe this passage with richer motion". Quantified: 4/6 shots had 42-72% static frames, with the longest static stretch at 2.8 s; the SC04 highlight moment, in motion throughout, was clearly better looking. **The sample film "RAG" has the same problem, so "benchmark against the sample" can't filter it out.**
- Rule (user ruling, added to storyboard global constraint §9): every subtitle block's verb has an action that continues to the next beat; after entering, no complete stillness >30 frames; shots with no other camera move get a 1.0→1.05 slow push-in. Boundaries unchanged (one protagonist, one flicker, no added debris). Quantified: sample the content area at 320×180; a frame with mean per-frame grayscale change <0.35 is static; static ≤40%, longest ≤1 s (`scripts/motion_check.py`, now in the template).
- **Group-level checks (low-resolution `--scale` renders) are too lenient; re-measuring the final film's fin_frames is the criterion**: in v1, group-level was 48/48 passing, while re-measuring the final film found 11 shots over the limit (3 truly static, 8 with only small-area action: data packets, cursors). Group-level renders were changed to 0.5x + JPEG q80, and `--frames` mode now outputs an extra column "full-resolution changed pixel count within the longest static stretch" to distinguish truly static (<800) from small-area action. The fix for small-area action is **increasing amplitude** (moving elements brighter, bigger, denser; the protagonist itself breathing ±2% over 30 frames), not adding elements.
- A 1.05 slow push-in contributes almost nothing at 320×180 sampling; it is an "always-moving layer" for the viewer, not for the metric.

## Camera movement and safe areas
- After a 1.05 slow push-in around (640,360), content must land within **x 89-1191 / y 122-607**; for 1.25-1.3 push-ins compute proportionally; layouts filling left to right (profiler panel x190-1090) are better off without a slow push-in. In carry-over displacements, pills must not scale with the group (font size drops below 22 or the pill gets too wide); interpolate geometry independently.
- **Camera moves should finish before the beat rather than start at the beat** (G2 SC09 moved the whole-group translation from 1616-1642 forward to 1590-1616, and only then did the label land at beat ±0). "No new elements enter during a camera move" only constrains new elements outside the camera layer: pills translating along with the rigid body can SoftIn during the translation (G4 SC20's QC medium item was exactly from not doing this).
- Slow push-ins that carry across two shots must be continuous (SC12 1.0→1.02, SC13 1.02→1.05, SC14 pushes in starting from 1.05), otherwise the boundary frame jumps.
